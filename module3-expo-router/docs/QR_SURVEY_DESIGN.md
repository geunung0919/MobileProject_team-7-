# QR 설문 데이터 수집 설계 (미연동)

현재 설문 문항/폼 URL을 받지 않았으므로 QR 생성, 폼 게시, 응답 수집, 설문 데이터 업로드는 구현하지 않는다. 앱 실행만으로 설문이나 개인정보를 전송하지 않는다.

## 수집 흐름
1. 문항 확정 → 설문 제공자(예: Google Forms)와 공개 폼 URL 결정 → 목적·보관기간·동의 안내.
2. 공개 응답 URL로 QR 생성. 관리자 페이지 URL, API 키, 사용자 ID를 QR에 넣지 않는다.
3. 참여자는 QR을 스캔해 폼에서 동의 후 응답한다. 참여하지 않아도 앱을 사용할 수 있다.
4. 담당자가 CSV/JSON으로 응답을 내보낸다. 서버 전용 임포터에서 필드 매핑, 값 검증, 중복 제거 후 Firestore에 저장한다.
5. 관리자만 원본 응답에 접근하고, 앱에는 집계 결과 또는 사용자 본인이 명시적으로 연결한 설정만 전달한다.

## 데이터 계약 초안 (설문을 받은 뒤 확정)
- surveyId, schemaVersion: 설문과 문항 버전. 변경 시 과거 응답을 덮어쓰지 않는다.
- responseId: 서버에서 발급한 응답 식별자.
- sourceResponseId: 설문 제공자 응답 ID 또는 서버가 만든 안정적 해시. 재임포트 중복 방지.
- consent: { accepted, version, acceptedAt }. 동의 문항이 없는 응답을 자동 동의로 처리하지 않는다.
- answers: { livingMonths?, cookingDaysPerWeek?, cookingTools?, inventoryDifficulties?, recipeReminderPreference? }.
- submittedAt, importedAt: 시간대 포함 타임스탬프. 가져올 수 없는 값은 추정하지 않는다.
- accountLink: 기본 null. 익명 설문을 이름/이메일로 앱 사용자와 자동 매칭하지 않는다.
- ingestionStatus: validated / rejected. 오류 사유는 별도 관리자 검수 기록에 남긴다.

확정 후 제안 경로: surveyDefinitions/{surveyId}, surveyResponses/{responseId}, surveyAggregates/{surveyId}.
이는 설계안이며 앱의 현재 AsyncStorage 또는 기존 재고 데이터에 실제 생성하지 않는다.

## 검증과 접근 제어
- 서버만 임포트 가능. 일반 앱은 원본 응답 읽기/쓰기를 금지한다.
- 수치 범위(예: 요리 빈도 0~7), enum, 배열 길이, 문자열 길이, 필수 동의를 검증한다.
- 모르는 질문/선택지는 버리지 않고 검수 대상으로 분리한다. 누락 값과 0/빈 배열을 구분한다.
- 제공자 응답 ID가 없으면 중복 판별 방식과 동일 응답 충돌 처리를 먼저 결정한다.
- 인증 사용자와 연결하려면 일회성 연결 코드와 별도 동의를 사용하고 서버에서 UID를 결정한다.
- 원본 보관기간/철회/삭제 절차와 책임자를 설문 게시 전에 정한다.
- 소규모 집계에서 특정 참여자가 드러나지 않게 공개 단위를 정한다.

## 추천에 사용되는 데이터 구분
설문은 수요 조사와 초기 추천 기준 검토용이다. 실제 소비/재고 기록이나 AI 학습 데이터로 둔갑시키지 않는다.
식재료 소진 예측은 앱에서 기록한 실제 요리·폐기·취소 내역을 분리해 평가한다.
설문에서 알림을 원한다고 답해도 휴대폰 알림 권한이나 앱 예약 설정을 자동 활성화하지 않는다.

## 설문을 받은 뒤 필요한 작업
문항/선택지 및 동의 문구 확정 → 샘플 응답 1건으로 매핑 → 임포트 미리보기 → 중복/오류 확인 → 서버 저장 → 집계 검증.
아직 수집된 응답, 응답자 수, 분석 결과는 없다.
